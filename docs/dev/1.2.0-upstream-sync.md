# Upstream Spotykach v1.2.0 sync analysis

Assessment of what changed in the upstream [Synthux Academy Spotykach](https://github.com/Synthux-Academy/Spotykach) firmware between the point sk-engines forked and its current v1.2.0 release, and which of those changes are worth adopting here.

## Fork point

sk-engines forked from upstream at exactly **v1.0.2** (`9627f2a`, "Patches 1.0.2", 2026-05-22). The last upstream commits in our history are that commit plus `a7c7f1f` ("Submodules"); sk-engines-specific work begins at `cb57e96` ("added review", 2026-05-29). Upstream has since shipped **v1.1.0** (2026-06-18) and **v1.2.0** (2026-07-03).

Diffing `v1.0.2..v1.2.0` upstream touches 37 files (~1080/-1010 lines). Despite the release-note attribution, nearly all the code actually landed in **v1.1.0**; v1.2.0 was a small top-up (FX-controller and clock-timing fixes).

To reproduce:

```
git remote add upstream https://github.com/Synthux-Academy/Spotykach.git
git fetch upstream --tags
git diff --stat v1.0.2 v1.2.0
```

## Why the split matters

sk-engines is a platform/engine fork. The granular engine (`src/engine/granular/`) is a deliberately frozen copy of the upstream Core kept as the compatibility reference; releases ship only the engines that are *new* to sk-engines. So upstream changes fall into two buckets with very different value:

- **Platform-level** changes (transport/clock, MIDI, hardware, storage) benefit every engine and are worth porting into the corresponding sk-engines subsystem.

- **Granular-DSP** changes benefit only the frozen stock engine and are high-cost / low-strategic-value to chase.

## Bucket A - platform-level (benefits all engines)

| Upstream change | In sk-engines? | Value | Cost |
|---|---|---|---|
| Clock recovery + beat-alignment (`driver.cpp`) | No - `Transport::tick()` is the naive v1.0.2 form | High | Low-Med |
| USB MIDI (device MIDI over the rear USB-C, new `core.midi.cpp`) | No - UART-only (`MidiUartHandler`) | High | Med |
| SD-slot selection off-by-one (`val*N` -> `round(val*(N-1))`) | **No - the exact bug is still present** | Med | Trivial |
| MIDI CC for Play/Rev/Rec | Superseded - sk routes generic MIDI to engines via `handle_midi_*` | Low | - |
| Lowercase `.wav` extension | No (sk uses `.WAV`) | Low / risky (breaks existing-card compat) | Trivial |
| Load/save interruption guards | Partially present - sk already has `is_idle()` guards in `pads.cpp` | Low | - |

### Clock recovery + beat-alignment (highest functional value)

Upstream v1.2.0 rewrote `Driver::tick()` so that, in external-clock mode, if no external tick arrives for over ~1s the clock is stopped and the divider counts are force-reset; the next incoming tick restarts and re-aligns to the downbeat. This fixes two reported bugs: audio no longer stalls after the external clock drops out, and playback auto-aligns to the first beat of a returning clock.

sk-engines' `Transport::tick()` is the pre-fix v1.0.2 form:

```cpp
void Transport::tick(const bool external_tick) {
    _clock.Tick(external_tick);
    if (_clock.ExternalClock()) return;
    _clock.SetTempo(_tempo.bpm());
}
```

When an external TS4/MIDI clock stops, `SynClock` sets `_hold` and freezes the internal timeline waiting for a tick that never comes, so playback stalls. This affects every engine that syncs to external clock.

**Port note:** do *not* copy upstream's else-branch verbatim. Upstream calls `_clock.SetTempo(_tempo.bpm())` unconditionally; sk-engines deliberately guards it (`if (ExternalClock()) return;`) because `SynClock::SetTempo` has side effects in external mode (toggles running state and calls `Reset()`). The port must keep that guard. sk-engines also tracks the last-external-tick timestamp as `_reset_us` via `ITimeSource` (not a Daisy hardware timer), so the 1s dropout test uses `now_us() - _reset_us >= 1000000`.

### USB MIDI

Upstream added a parallel `MidiUsbHandler` on the `EXTERNAL` USB peripheral (`MidiUsbTransport::Config::Periph::EXTERNAL`) alongside the existing UART MIDI, and merges both event streams. On this hardware the `EXTERNAL` peripheral is the rear USB-C connector already wired to the host for DFU flashing, so plugging that port into a computer presents the device as a class-compliant MIDI device.

sk-engines is currently UART-only. `Log::StartLog` uses the Seed's *internal* USB port, so USB MIDI on `EXTERNAL` does not conflict with logging. This benefits the MIDI-driven synth engines (csound, chuck, mosc, reso). `MidiUsbHandler` / `MidiUsbTransport` with the `EXTERNAL` periph are present in the pinned libDaisy fork. Firmware-only change - not exercised by host tests, needs hardware verification.

### SD-slot selection off-by-one (confirmed bug)

`src/ui/core.ui.cpp` (both decks):

```cpp
select_slot_at(val * kStorageSlotCount);   // val in [0,1], N=6
```

With `select_slot_at` rejecting `idx >= N`, the last slot (index 5) is only reachable in a razor-thin band as `val -> 1` before the product hits 6 and is rejected, and the mapping across slots is uneven. Upstream v1.1.0 fixed this to `std::round(val * (kStorageSlotCount - 1))`. This is the granular SD slot picker and any engine reusing that storage UI.

## Bucket B - granular-DSP only (benefits only the frozen stock engine)

The large v1.1.0 refactor - slices renamed to "cues", `apply_dimensions()` rewrite, start/size continuous modulation, **WAV cue-point import** (read cue markers embedded in a WAV to define slice points), slice-mono config, plus the "Drift-mode size application" and "quantized-pitch capture" fixes - is a deeply intertwined rewrite of `Deck` + `Generator`, not cherry-pickable. Because sk-engines' granular is the compatibility reference and not a headline engine, porting it is high-cost / low-value. The one arguably interesting *feature* is WAV cue-point import, but it is welded into the whole cue refactor. Deferred.

## Recommendation (ranked) and status

1. **SD-slot off-by-one fix** - trivial, confirmed bug. **Done.**

2. **Clock recovery + beat-alignment port** into `Transport` - high value, all engines, contained. **Done.**

3. **USB MIDI** - high value for synth engines, moderate effort, needs hardware verification. **Done (host-built; hardware test pending).**

4. Skip lowercase `.wav` (cosmetic + breaks existing-card compat), skip the CC map (sk has a better generic model), defer the granular cue refactor unless WAV-cue slicing is wanted in the stock engine.

## WAV cue-point import, reframed as a platform capability (`CapWavCues`)

Rather than adopt upstream's design - cue parsing welded into the granular `Generator` - the WAV-cue *feature* is separated the sk way: the platform parses generically, the engine assigns meaning. This decouples it from the deferred granular DSP rewrite and makes it reusable by any engine that loads WAV files.

**Platform half (done, host-tested, size-neutral):**

- `src/engine/wav_cues.h` - `struct WavCues { size_t frames[32]; uint8_t count; }`, markers as sample-frame offsets (bit-depth agnostic).
- `src/memory/wav.h` - `find_cue_points(bytes, size, frame_limit, WavCues&)`, a pure, bounds-checked chunk-walk for the `cue ` chunk (order-independent, drops out-of-range markers, clamps to `kMax`). Corrects an upstream over-read (it read `size_t` for the 4-byte `dwSampleOffset`, which only happened to work because `size_t` is 4 bytes on the 32-bit target).
- `CapWavCues` (`engine_params.h`, bit 11) + `IEngine::on_wav_cues(DeckRef::Ref, const WavCues&)` (default no-op). The platform calls it after a WAV load, only for engines that advertise the capability.
- `host/test_wav_cues.cpp` - 7 cases (basic parse, chunk-order independence, `frame_limit` filter, missing chunk, `kMax` clamp, truncated chunk, non-RIFF). Wired into `make -C host test`.
- Cost: one vtable slot (granular 94.06% -> 94.07% SRAM_EXEC, +8 bytes); every engine still links.

**Not yet done (needs a consumer decision):**

- Load-path wiring: invoke `on_wav_cues` at load completion in the in-RAM path (`storage.cpp`/`card.cpp`) and the streaming path (`IStreamDeck` / `WavStreamReader::begin`, which already walks past the `cue ` chunk). Best built together with the first consumer so it can be exercised.
- A consumer engine that gives the markers meaning (candidates: shuttle jump/loop markers, softcut loop points, a new slicer demo; granular Slice would reopen the frozen `Deck`/`Generator`).
